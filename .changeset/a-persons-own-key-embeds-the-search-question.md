The canvas agent gains `search_blueprint`, ranked retrieval for when a caller has words but not a name or an id — and it is OFF unless a deployment says otherwise, because it is the one read that needs a database function this template's schema does not ship. A deployment whose database carries `search_blueprint` sets `agent.search.enabled` on its `DeploymentConfig`; with it false or absent the tool is not on the agent's roster at all, so nothing in the session refers to a capability the database does not have. Results are ranked and cut at `limit` (default 15, at most 100) under a header with the corpus-wide total, every row reports `matched_by`, and the same `phase`, `scenario`, `kind`, `lane_role` and `service` narrowing the journey reads take applies here. Meaning results are held inside the scoped service, like every other read.

A person's own provider key can now embed their search question, so a question asked in the person's own words can match a cell that says the same thing differently. `agent.search.indexes` lists the vector indexes a deployment's database holds — `{ provider, model, dimensions }`, `provider` being `google` or `openai` — and when the person's current chat provider matches an entry, the question is embedded in their browser with their own key, at that entry's model and size, and sent to the function as `query_embedding` plus `embed_model`. Two keys, one model: the person's key embeds the question, the deployment's own job embeds the cells with a server-held credential. The template holds no such credential and builds no index. Google embeds through the Gemini API's `embedContent` with the key in `x-goog-api-key` — never a query string, so it cannot leak through history, proxies or referrers — as `RETRIEVAL_QUERY`, against cells the deployment embedded as `RETRIEVAL_DOCUMENT`. OpenAI embeds through its embeddings endpoint with an `Authorization` header and the listed size, so serving OpenAI-key users later is a deployment's index and config, not another template change. Anthropic has no embedding model and is never listed.

Listing no index is a supported state: the tool is offered and matches words and structure only. Listing an index a person's provider cannot reach is different — those people are not offered the tool, quietly, rather than being handed keyword search dressed as the search everyone else gets. When a listed index was supposed to run and the embed fails (a rate limit, an outage, or the function raising `embedding model mismatch`), the search falls back to exactly one words-and-structure call; every other database error surfaces, so a broken search is never reported as a search that found nothing. The tool's text names the arms that actually ran, and its zero-row answer says what their silence does and does not prove.

A scoped search tells the truth about what the scope did. The header keeps the function's own corpus-wide total — the function clips at `match_count` before any scope filter can run, so retotalling to the kept count would report a clipped top-k as the whole matching set — and reads `N shown, in <service>, of T matching across the deployment`. Rows that matched in another service are reported as that, not as nothing matching. Rows are placed by phase name because the function returns no ids, and `phases.name` is not unique across services, so a name two services share places nothing: those rows are dropped, counted and named in the text rather than handed to the wrong service. The connector doc states that every row must carry its phase breadcrumb, and that a deployment with several services should give its phases distinct names.

Every way an embed can fail is one `EmbedQuestionError`, so a bad connection cannot read as an empty blueprint: a non-`ok` response, a `fetch` that rejects (offline, DNS, TLS, a blocked host), a body that is not JSON, a vector of a width the listed index does not hold, and an eight-second stall all fall back to words and structure. A caller's own abort passes through untouched — pressing Stop must not start a keyword search nobody asked for — and the run's signal now reaches the embed through `DispatchContext`. A rung outside the vocabulary is refused before anything is embedded or read, the way `list_blueprint` refuses one, and `limit` has a floor as well as a cap, because `limit: 0` would have asked the function for nothing and rendered as "no row uses those words".

The roster gates now live in one exported `sessionRoster` in `src/lib/agent/tools/specs.ts`, where their ordering is stated and tested rather than nested in the loop. `dispatchTool` takes an optional `DispatchContext` carrying what a session may reach that another may not. `search_blueprint` is on the mobile reading roster — a phone's question is the case for it — and absent from the no-database trial, which has no function to call. The connector doc states the function's argument and column contract, the `embedding model mismatch` requirement, and the task-type pairing; `references/customization.md` shows the config.
